§ 01

Division of labour

Several things a server might expect to handle are already solved on the device. Knowing which saves you building them twice.

Client owns
  • Media capture and the GPS gate
  • Local persistence of media and metadata
  • The outbox queue and its state machine
  • Retry scheduling and exponential backoff
  • Background upload continuation
  • Connectivity detection, Wi-Fi-only deferral
  • Chunk resumption bookkeeping
  • Rendering of vetting state and privacy flags
Server owns
  • Durable storage and media hosting
  • Vetting decisions and routing
  • The public feed and its ordering
  • Map clustering
  • Org saved queries and matching
  • Authorisation, in full
  • Abuse handling and lawful process

Both own display-flag enforcement. That is deliberate duplication, not redundancy — see §07.

§ 04

API layer

Specified

Every screen is built against one swappable interface, with two implementations selected by a single environment variable.

.envenv
EXPO_PUBLIC_API_MODE=mock   → MockApiClient — seeded fixtures, artificial
                              latency, injectable failure rate, no backend
EXPO_PUBLIC_API_MODE=http   → HttpApiClient — real calls to API_URL

This is why frontend work never blocks on the backend, and why the contract is already exercised end to end before a server exists.

What this means for you

The client never constructs a request inline in a component. If your implementation needs to differ from the contract, the change lands in exactly one file — so raise differences early rather than working around them.

§ 05

The GPS gate

Specified

The defining feature. The camera preview does not mount until a location fix meets the accuracy threshold. This is a hard gate, not a warning.

  entering capture
        │
        ▼
  watchPositionAsync(BestForNavigation)
        │
        ├─ permission denied ──────► explainer + deep link to settings
        ├─ location services off ──► prompt to enable
        │
        ▼
  acquiring  accuracy readout · pulse indicator · live lat/long at 6 dp
        │
        ├─ accuracy ≤ 20 m ────────► CAMERA MOUNTS  (haptic confirmation)
        │
        └─ stalled > 30 s ─────────► "move to an open area" coaching
                                     └─ optional escape hatch:
                                        proceed, flagged confidence: "low"
ConstantValueRationale
GPS_ACCURACY_THRESHOLD_M20About the best a consumer phone achieves outdoors within a few seconds. Tighter feels broken in urban canyons; looser is useless for sending someone to the scene.
GPS_STALL_TIMEOUT_MS30 000When coaching and the escape hatch appear.
GPS_ABSOLUTE_MAX_ACCURACY_M150Beyond this, not offered even via the escape hatch.
MAX_VIDEO_DURATION_S60Enforced client-side with a ring countdown.

The fix is locked at the moment of capture and does not keep updating afterwards.

Tamper signals sent alongside it: accuracyM, altitude, heading, speed, capturedAtIso (device clock), capturedAtUtcOffsetMinutes, deviceUptimeMs, and isMocked on Android. The reduced-accuracy escape hatch flags the report — it never silently downgrades it, and the flag is visible in the UI as well as the payload.

§ 06

Offline sync

Specified

The network is treated as absent by default. Capture always succeeds locally.

On capture the client writes the media file to documentDirectory/incidents/ — never the cache directory, which the OS can evict — and inserts a row in the local incidents table. Only when both succeed does the UI report success.

Local record state machine

  draft ──► queued ──► uploading ──► uploaded
                        │
                        └──► failed ──► (retry) ──► queued

  any state ──► cancelled   terminal, user-initiated

Persisted per row: attemptCount, lastError, nextRetryAt, serverId, bytesUploaded.

Drain rules

  • Drains when isInternetReachable === true — not merely isConnected, which is true on a captive-portal Wi-Fi that goes nowhere.
  • Oldest first, one item at a time.
  • A background task continues uploads when the app is backgrounded. iOS background execution is opportunistic and not guaranteed — the app also resumes draining on foreground. This is documented, not assumed away.
  • Wi-Fi-only toggle defers video uploads to Wi-Fi; photos still go over mobile data. The outbox shows what is waiting and why.
Consequence for retention

The local media file is deleted only after the server confirms completion. The metadata row is kept, with serverId, so the reporter retains a personal history.

Which is why media retention is question 1 in the contract's open questions: if the server expires footage the client has already deleted, the user's own history points at nothing.

§ 07

Privacy enforcement

Specified

Three booleans per report: showLocation, showDate, showTime. The client enforces these independently of the server, with unit tests asserting a hidden value never reaches rendered output.

Why both layers exist

Client-side hiding alone means true coordinates travel to every phone that scrolls past the report and sit in an inspectable cache. Server-side alone means one client bug leaks them. Neither layer is the backup for the other.

The review screen shows a live public preview — exactly what a stranger will see — so the reporter is never guessing what they are about to publish.

Anonymous mode

A prominent toggle with an honest explainer sheet. The copy states that anonymous means the public and other users see no profile, but a device identifier is still attached for abuse prevention and accountability. The client deliberately does not overstate the guarantee — and deviceId is never rendered in the public UI, on any screen.

§ 08

Device identity

Specified
  • A UUID v4 generated on first launch, persisted in the secure keychain. Primary identifier, sent as X-Device-Id on every request.
  • Supplemented by the Android ID / iOS identifierForVendor as a secondary field.
  • Both platform IDs reset on uninstall or factory reset and are not stable. Treat them as a weak correlation signal; the keychain UUID is the primary.
§ 09

Design system

Built

Tokens live as CSS custom properties, surfaced as Tailwind utilities. Components never hardcode a hex value.

The palette is tuned for a 70-year-old reader, which drove some non-obvious choices:

  • Light by default, not dark. Intraocular light scatter roughly doubles between 20 and 70, so white-on-black haloes badly. Dark mode is a young-eye preference.
  • WCAG AAA (7:1) for body text, not AA — contrast sensitivity falls sharply after 60.
  • Warm paper, not pure white — #FFFFFF at phone brightness causes veiling glare.
  • Warm hues. The aging lens yellows and absorbs short wavelengths, so blues muddy. Blue never carries meaning alone.
  • 17px body type, 48pt tap targets.

Category colours are grouped into families so hue signals the kind of incident and the label says which one. Colour is a secondary cue — twelve hues cannot be reliably distinguished by an older eye, so every chip carries a text label and every map pin gets a distinct icon.

All of this is enforced by 33 test assertions, not just documented — a later "soften that grey" fails CI.

§ 11

Takeaways

If you read nothing else in this document, read these five.

Because the client…You should…
is offline-first and retries foreverAssume duplicates. Implement idempotency keys — this is not optional.
already backs off on 429 and 5xxReturn the correct status and it behaves. Return 500 for a validation error and every affected phone retries hourly, indefinitely.
deletes local media on upload completionTreat retention as a product decision, not an internal detail — it changes what a reporter sees in their own history.
enforces display flags tooStill suppress at source. That is defence in depth, not permission to send suppressed values.
is built against one swappable interfaceRaise contract differences now. Cheap today, expensive once the screens exist.
