GhanaMediaWatch Backend Spec

A GPS-gated incident reporting app for Ghana. The camera does not unlock until the device holds an accurate fix; capture always succeeds offline; the queue drains itself when connectivity returns. This is everything the server has to provide for that to work.

§ 00

What you're building

Members of the public film incidents — floods, fires, road accidents, illegal mining, power failures — and the app stamps each one with verified coordinates and a timestamp before it ever reaches you. Some reports publish straight to a public feed; some need review first. Institutions subscribe to standing queries over the same crowd-sourced pool.

Four behaviours that shape the API

BehaviourWhat it means for the server
GPS gate The camera will not mount until horizontal accuracy reaches 20 m. Every submission therefore arrives with a real fix and an accuracyM. Reports captured through the reduced-accuracy escape hatch are flagged confidence: "low" rather than silently downgraded.
Offline-first Capture writes to local storage and a SQLite outbox. Uploads happen later, possibly days later, possibly from a different network. Assume every request may be a retry — idempotency is not optional.
Vetting Reports carry a state. The public feed serves only published. The author sees all of their own, with reasons.
Selective disclosure A reporter can publish footage while hiding its location, date, or time. This is a privacy guarantee, not a UI preference — see §07.

What the client already handles

So you don't build it twice: local media storage, the SQLite outbox and its state machine, exponential backoff with jitter, background upload scheduling, chunk resumption bookkeeping, connectivity detection, and Wi-Fi-only deferral for video. The server sees the result, not the machinery.

§ 01

Conventions

Authentication

Bearer JWT. Short-lived access token (proposed 15 min), long-lived refresh token (proposed 60 days) held in the device keychain. Three caller identities, and every endpoint below names which it accepts.

IdentityObtained viaCan do
devicePOST /devicesSubmit incidents, read the public feed. No profile.
userPOST /auth/signinEverything above, plus own-report management and interactions.
org_memberPOST /auth/signinAdds the /org/* surface, scoped by role.

Headers on every request

HeaderNotes
AuthorizationExcept POST /devices and /auth/*.
X-Device-IdThe keychain UUID. Sent always, authenticated or not — including on anonymous submissions.
X-Client-VersionApp version and build, for support triage.
X-Platformandroid or ios.
Idempotency-KeyUUID v4. Required on every state-creating POST.
Must — idempotency

Capture happens offline and the outbox retries. The same submission will arrive more than once. On a repeated Idempotency-Key within 24 hours, return the original response and status code — not a conflict. Without this, a reporter on a flaky connection publishes the same incident three times to a public feed.

Error envelope

Every non-2xx uses exactly this shape. No bare strings, no HTML error pages.

Response · any 4xx / 5xxjson
{
  "error": {
    "code": "GPS_ACCURACY_REJECTED",
    "message": "Location accuracy of 84 m exceeds the 20 m limit.",
    "details": { "accuracyM": 84, "limitM": 20 },
    "requestId": "01JBX7Q2K9"
  }
}
  • code — stable SCREAMING_SNAKE_CASE. The client switches on this, never on message.
  • message — developer-facing English. Never shown to users; the client maps code to a localised string.
  • requestId — echoed into the client's bug reports. Log it.

Pagination — cursor, not offset

The feed shifts under the reader as reports clear review, so offsets would duplicate and skip. Return { items, nextCursor, hasMore }; nextCursor is null when exhausted and opaque to the client — encode whatever you like in it. limit defaults to 20, caps at 50. Never return a total; it is expensive and unused.

Time and coordinates

  • Server timestamps are ISO 8601 UTC with Z.
  • Device capture time is separate and untrusted. The client sends capturedAtIso, capturedAtUtcOffsetMinutes, and deviceUptimeMs. Store all three — a device clock inconsistent with its uptime or with server receipt time is a tamper signal for vetting.
  • Coordinates: decimal degrees, WGS 84, JSON numbers at 6 dp (~0.11 m). Never strings.
  • Distances in metres, durations in ms, sizes in bytes. Integers unless noted.

§ 03

Identity & anonymity

The client generates a UUID v4 on first launch and keeps it in the secure keychain. That is the primary device identifier, sent as X-Device-Id on every request. It also sends a secondary platform identifier — Android ID, or iOS identifierForVendor.

Must — what anonymity means here

deviceId is attached to anonymous submissions too. That is the accountability mechanism the product depends on, and the app tells users so plainly before they publish.

In return, the public API must never expose deviceId, the author's account, or any derived identifier on an anonymous report — not in the feed, not in detail, not in comments, not in an ETag or a media URL. You retain the link internally for abuse handling and lawful process. Do not implement anything that would make the app's explainer a lie.

Both platform identifiers reset on uninstall or factory reset and are not stable. Treat them as a weak correlation signal, never a primary key.

§ 04

Upload protocol

A 60-second video over Ghanaian mobile data will drop mid-flight. Uploads are resumable and chunked, in three phases.

Phase 1 · init
POST /incidents

Metadata only, no bytes. Returns an uploadId and the chunk plan.

Phase 2 · transfer
PUT /uploads/{id}/chunks/{n}

Raw bytes. Repeatable and order-independent, because retries reorder.

Phase 3 · commit
POST /uploads/{id}/complete

Server assembles, verifies the hash, enqueues for vetting.

If the app dies mid-upload, the client calls GET /uploads/{id} on next launch to learn which chunks you already hold, then resumes. It does not restart from zero.

POST/incidentsdevice · user

Metadata only. Requires Idempotency-Key.

Request bodyjson
{
  "clientId": "e3a1…",                // the client's local row id
  "category": "flood",
  "description": "Culvert blocked, road impassable.",
  "isAnonymous": true,
  "displayFlags": { "showLocation": true,
                    "showDate": true,
                    "showTime": false },

  "location": {
    "latitude": 5.603717, "longitude": -0.186964,
    "accuracyM": 8.4, "altitude": 61.2,
    "heading": 142.0, "speed": 0.0,
    "confidence": "high", "isMocked": false
  },

  "capturedAtIso": "2026-08-19T14:31:00.000Z",
  "capturedAtUtcOffsetMinutes": 0,
  "deviceUptimeMs": 184523110,      // tamper signal

  "media": {
    "kind": "video", "mimeType": "video/mp4",
    "byteSize": 8421376, "durationMs": 24500,
    "width": 1080, "height": 1920,
    "sha256": "9f86d081884c7d65…"
  }
}
Response · 201json
{ "incidentId": "inc_01JBX7Q2K9",
  "uploadId": "upl_01JBX7Q2K9",
  "chunkSizeBytes": 5242880,
  "chunkCount": 2,
  "expiresAt": "2026-08-20T14:31:00.000Z" }

The client proposes 5 MiB chunks, but your response is authoritative — it will use whatever chunkSizeBytes you return. Echo clientId back on the resulting incident so the outbox reconciles without relying on ordering.

PUT/uploads/{uploadId}/chunks/{index}device · user

index is 0-based. Body is application/octet-stream — raw bytes, no multipart wrapper. Returns { index, received, bytesReceived }.

Must be idempotent. Re-sending a chunk you already hold returns 200, not an error.

POST/uploads/{uploadId}/completedevice · user

Empty body. Returns the full incident in its author shape, with vettingState set by your routing rules.

Verify sha256 here and reject with MEDIA_HASH_MISMATCH on a mismatch — that is the client's signal to re-upload rather than silently publishing corrupt footage.

Only after this succeeds does the client delete its local media file. It keeps the metadata row so the reporter retains a personal history — which is why media retention is an open question.

GET/uploads/{uploadId}device · user

Resume support. Returns receivedChunks: [0] so the client sends only what is missing. If the window has elapsed, return 410 UPLOAD_EXPIRED and the client restarts from POST /incidents.

§ 05

Reading endpoints

GET/incidentsdevice · user

The public feed. Returns only published. Never leak another state here.

ParamNotes
limit, cursorCursor pagination, see §01.
categoryRepeatable; multiple values mean OR.
nearlat,lng — enables distanceM on each item.
radiusMRequires near.
since, untilISO 8601, applied to publishedAt.
sortrecent (default) or nearby.
GET/incidents/mapdevice · user

The map tab needs clusters, not a page of full records. ?bbox=-0.3,5.5,-0.1,5.7&zoom=12 returns { clusters: [{ latitude, longitude, count, categories }], markers: [...] }.

Cluster server-side. Returning 4,000 raw points and clustering on-device will not hold 60 fps on a mid-range Android phone.

GET/incidents/{id}device · user

Public shape. If it is not published and the caller is not the author, return 404 INCIDENT_NOT_FOUND — not 403, which would confirm the report exists.

GET/me/incidentsuser

All states, author shape, with rejectionReason where applicable. Filter with ?state=pending_review.

PATCH/incidents/{id}user · author only

The account owner can change displayFlags after publication — that is a product requirement, not an edge case.

Also accepts description. Editing the description after publication must re-enter review, otherwise it is a trivial bait-and-switch on approved footage.

DELETE/incidents/{id}user · author only

Soft-delete. Returns 204.

§ 06

Vetting

Every report enters at pending_review and leaves to exactly one terminal state.

StateIn feed?Author sees?Meaning
pending_reviewNoYes, with a banner Awaiting a human or automated decision.
publishedYesYes Cleared for public display.
rejectedNoYes, with the reason Declined. rejectionReason is shown to the reporter verbatim — write it for them, not for staff.
restrictedNoYes, with a banner Held for security sensitivity. Visible to authorised org accounts only.

The brief allows reports to be "vetted or automatically uploaded … based on public or security sensitivity". The client does not decide this — it renders whatever state you return. Which categories auto-publish, and who triggers human review, is question 3.

§ 07

Display flags

Read this section twice. Its failure mode is exposing a reporter's location.

Each report carries three booleans, set by the reporter at review time and editable later: showLocation, showDate, showTime. They are display flags, not storage flags — you still store the true coordinates and capture timestamp for every report, always, because vetting, abuse investigation, and lawful requests all depend on it.

Must — suppress at the source

On any endpoint serving a public audience — feed, map, public detail, comments — the server must omit or null the suppressed fields. Do not send them and trust the client to hide them.

When falsePublic responses must…
showLocation Null latitude, longitude, and label. Also drop the item from /incidents/map and from near/radiusM filtering — a marker on a map is a location disclosure.
showDate Null capturedAtIso. Use publishedAt truncated to the hour if you need an ordering key.
showTime Truncate capturedAtIso to midnight UTC.

The client enforces the identical rules independently, with unit tests asserting a hidden value never renders. Both layers are required. Client-side hiding alone means the true coordinates travel to every phone that scrolls past the report and sit in an inspectable cache. Server-side alone means one client bug leaks them. Defence in depth is not negotiable here.

If showDate is false but showTime is true, suppress both — a bare time with no date is meaningless and still narrows the window. The client greys out that combination, but do not rely on it.

§ 08

Org tier

Institutions and businesses subscribe to standing queries over the crowd-sourced pool.

Must — authorisation

The client hides /org routes from non-members as a courtesy. That is not authorisation. Every endpoint here must independently enforce membership and role. Roles: owner, admin, analyst, viewer.

GET/org/dashboardorg_member

Counts by category and by state, a daily trend series for the sparkline, and recent high-priority reports.

GETPOST /org/queriesorg_member

An org's standing watch criteria — categories, keywords, a geofence, a time window, and alert preferences.

Saved queryjson
{
  "name": "Flooding — Odaw catchment",
  "categories": ["flood", "infrastructure"],
  "keywords": ["culvert", "drain"],
  "geofence": {
    "kind": "circle",          // or "polygon" + points[]
    "center": { "latitude": 5.603717, "longitude": -0.186964 },
    "radiusM": 3000
  },
  "timeWindow": { "since": "2026-08-01T00:00:00.000Z" },
  "alerts": { "push": true, "email": false }
}

A saved query must never match a report whose showLocation is false via its geofence. Suppressed location means suppressed from location-based matching — including for paying customers.

POST/org/incidents/{id}/status · /notesorg_member

Inbox triage: in_review, actioned, dismissed; plus internal notes that are never public.

POST/org/exportsorg_member

Returns 202 with an exportId. The client polls GET /org/exports/{id} until ready, then hands the URL to the OS share sheet.

Async, not a blocking download — a 90-day CSV will time out a mobile request.

Must — retryable vs terminal

The outbox retries 429, 5xx, and network failures forever with backoff (2s → 8s → 30s → 2m → 10m → 1h). It fails an item permanently on 400, 403, 413, and 422.

Returning 500 for what is really a validation error means every affected phone retries a doomed upload, hourly, indefinitely.
